# BudgetControl Sync

Prototype for manual, read-only Enable Banking expense synchronization. The Gateway authenticates the caller and forwards trusted identity and workspace context. This service allows only `marco.defelice890@gmail.com` and owns the provider integration, authorization flow and connection records. Entries owns expense creation and atomic duplicate detection.

## Setup

1. Install PHP 8.1+, Composer dependencies, the cURL and OpenSSL extensions, and configure the shared PostgreSQL database. Copy `.env.example` to `.env`.
2. Register an Enable Banking application for personal use, whitelist the bank accounts as required by the provider, and register the HTTPS callback `https://<app-host>/app/settings/open-banking`. Configure its application ID and mount its private key outside the repository. Set `ENABLE_BANKING_REDIRECT_URL` to exactly the registered URL.
3. Generate a random 32-byte key, encode it with base64 and set `SYNC_ENCRYPTION_KEY`. Keep it stable and secret. Set `SECRET_KEY` to the Gateway `API_SECRET`. Set `ENTRY_API_BASE_URL` and an independent `ENTRY_SYNC_SECRET`; configure the same value as `SYNC_API_SECRET` in Entries. Keep Sync and Entries on an internal network.
4. After the Schema Registry change has been released and the Composer dependency updated, run `vendor/bin/phinx migrate` against the same database used by Entries. The service uses the shared `ms_migrations` history. The schema registry migration creates `sync_imported_expenses`, which Entries writes atomically with an expense. Install a schema registry version containing `20261116000000_create_sync_tables.php` before running migrations. Deploy Entries, Sync, Gateway and PWA changes together.
5. Configure `SYNC_API_BASE_URL` in Gateway and `VUE_APP_SUPPORT_EMAIL` in the PWA. Connect a bank in the wallet screen, choose the account and expense settings, and start a manual sync.

Booked debits and credits with a stable `entry_reference`, account identification hash and matching currency are imported. Transactions missing these fields are counted as skipped. The categories chosen during manual setup are fallbacks: matching keywords from manually created entries may determine a category. Imported entries get the `sync` label; editing an entry removes the label, while its permanent import marker prevents reimport or overwrite. Historical manually imported entries are not automatically matched.

Manual sync saves validated account settings before importing transactions for the CommandJobs `bank:sync` command. The association remains saved even if the bank balance cannot be aligned. CommandJobs calls the internal `/internal/scheduled-sync` route with both `X-API-SECRET` and the independent `X-Sync-Job-Secret`, matching `SECRET_KEY` and `SYNC_JOB_SECRET` respectively. Configure the same job secret in both services. Renewed consent must be linked to the wallet again with a manual sync. Install and apply the Schema Registry migration `20261116010000_create_sync_account_settings.php` before deploying these changes.

After importing transactions, Sync aligns the wallet to the bank's current booked balance (interim booked preferred, then current closing booked). When neither is available, an interim or closing available balance is used instead; available balances can include pending activity. If no usable balance is returned, manual sync reports `balance_updated: false` and the PWA warns the user; the scheduled job reports a failure so the missing alignment is visible. The association and imported entries remain saved, and the final alignment leaves the wallet balance unchanged. The log records balance types, reference dates, currency match and amount format, without account details or amounts. The balance represents the bank snapshot at the last successful sync; it is not a real-time feed. Only one bank account can be mapped to a wallet. Existing bank connections are scoped to the user and workspace. Consent expiry requires a new connection. American Express is not supported by this integration.

No provider credentials, tokens, authorization codes, transaction payloads or sensitive request headers should be logged. Back up the database and encryption key together. Do not expose the service directly to the Internet. Enable Banking credentials and approved account access are required for a live run.

## Checks

Run `php Test/ManualSyncCheck.php` for eligibility, authorization replay, pagination and sync mapping checks. In Entries, run `php test/Integration/SyncExpenseCheck.php` for duplicate handling and transaction rollback. By default the Sync check uses SQLite; the GitHub Actions workflow runs it against an isolated PostgreSQL service. The checks use simulated bank responses; a real provider connection requires the registered application and whitelisted accounts.

## GitHub Actions

Pull requests to `main` and `develop` run the Sync checks against PostgreSQL. A push to `main` (or a manual production deployment) runs the same checks before deploying to the `prod` environment. A push to `develop` or a manual development deployment uses the `dev` environment and the same checks. Configure its `SFTP_USER`, `SFTP_HOST`, `SFTP_PORT`, `SFTP_PATH`, `SFTP_PASSWORD` and/or `SSH_PRIVATE_KEY` secrets for the Sync installation and ensure the host already has the `budgetcontrol-ms-sync` container and its private runtime configuration.

Version tags matching `v*.*.*`, or a manual run, build and push `${DOCKER_USERNAME}/sync:<ref>` using the `docker-prod` environment and its `DOCKER_USERNAME` and `DOCKER_PASSWORD` secrets. A manually triggered image build requires an explicit Docker image tag. All image builds run the same PostgreSQL checks first. The production workflow does not run database migrations; release the Schema Registry and migrate PostgreSQL separately before deploying code that depends on the new tables.
